## Production wave 5 assembly (8 October 2026, verification pending)

Wave 5 is assembled after the verifier's immutable schemas 42/43. New schemas 44â€“52 and aggregate `0026_platform_core.sql` include mixed output records, measured SLOs, recovery epochs, retention, audit exports, managed serving and billing. No Docker, networked PostgreSQL, Temporal, kind, browser or live cloud acceptance ran on this builder. [W5-ASSEMBLY.md](build/production/verify/W5-ASSEMBLY.md) records exact checks and deferred commands. Release flags remain false.

- **Managed onboarding and first deploy:** reconcile/drift use the same tenant-scoped session as execution. The first plan checks the existing namespace and isolation policies/RBAC before server validation. Missing or unverifiable namespaces refuse. Automatic isolation provisioning remains deferred: its private rendered digest is not DUR-B reviewed semantics and its apply authority is not DUR-C custody. Deploy approval cannot authorize privileged bootstrap. An operator must separately provision the approved tenant namespace, per-tenant operator credential and node pool. Default managed builds refuse until a per-tenant build custody adapter exists. No shared credential/build fallback. HTTPRoute drift compares rendered rules/matches/backends as well as ownership, parent, hostname and readiness. Declared HPA ownership excludes only replicas from configuration comparison; native image/resources checks remain. [Managed joins](build/production/verify/W5-MAN-JOINS.md).
- **Managed serving/isolation:** domain routes have handler contracts; ACME and IAM enforcement need real services. Ephemeral-storage LimitRange defaults change rendered/export digests, so re-review old plans. Runtime-class isolation and FQDN enforcement need a provisioned sandbox/pinned Cilium. CPU, PID, disk and latency limits are provisional, not operated acceptance.
- **Mixed functions fixture remains blocked:** an experimental `aws:lambda_function` driver exists for resource graphs, but Service v1/v2 manifests expose web/worker/cron only. Native config shape, artifact custody and an authenticated endpoint/invocation adapter are missing. The fixture's HTTPS/mTLS `/enrich` consumer cannot invoke that driver. The container substitution remains explicitly labelled; switching a kind name would misrepresent runnable Lambda acceptance. Protected cross-partition plans now require caller-supplied connectivity before persistence.
- **Recovery:** restore reports publish valid incident/snapshot/finish instants to the SLO recorder with source `recovery-drill`. No incident timestamp or unsuccessful restore produces an SLO measurement. Restore completion measures the fenced database restore, not application health restoration. Sink failure remains a named hand-off; post-snapshot effects still require provider reconciliation and Temporal continuation must be settled before workers start. Hosted SQLite needs the separate hand-off in RESTORE-RUNBOOK.
- **Keys/retention:** archives use `enc:archive`, HKDF-separated from `enc:backup`, resolved from externally supplied `ZENITH_BACKUP_KEY`. Pre-assembly archives using the backup key directly need explicit legacy-key restore; no silent fallback. Audit exports use `signing:audit-export` and `ZENITH_AUDIT_EXPORT_SIGNING_JWK`; absent keys refuse, workload/capability/release signing does not substitute. Local EdDSA only; audit KMS custody is not implemented. Retention still defaults to forever; deletion requires DEC-RETENTION plus `ZENITH_RETENTION_APPLY=1`, archive readback, and no legal hold. Authority, receipts, measurements, recovery and billing ledgers are never prunable.
- **Billing:** durable billing maintenance and fallback ticks share the OBS-04 lease/health record. Suspension checks follow quota admission; destroy/export remain available. Billing defaults disabled, test-mode Stripe only; actual payment/accounting acceptance and accountable tariffs remain deferred.
- **Release/security:** adversarial contracts remain required. Windows webhook ownership controls still require Linux verification. Runner/zenithd base-image digests, two managed-kind image digests and Cilium chart version/hash must be supplied and verified by the Mac verifier. A person must later create the protected release signing key and separately approve `docs/build/production/permissions.json` budgets. Permissions remain unapproved; no cloud call was made.

## Production wave 4 (7 October 2026, implementation complete, verification pending; live cloud acceptance deferred by decision)

Wave 4 added PROD-LIFE-03, LIFE-04, LIFE-05, LIFE-06, COST-01, COST-02, OPS-02, OPS-03, OPS-05, OPS-06 and MIX-01 to MIX-04, plus the Kubernetes one-connection join (K8S-CONN), on top of waves 1 to 3. Nothing below has been executed on a test machine: no vitest, go test, Docker, PostgreSQL, Temporal, kind or cloud run has covered these bytes, and no real cloud API was called. Every live harness is gated (`ZENITH_LIVE_<PROVIDER>=1` plus credential FILE references), skips with a stated reason without them and is never counted as passed. Per-requirement detail lives in `docs/build/production/verify/` ([VERIFY-QUEUE.md](build/production/VERIFY-QUEUE.md) has the ordered runbook; [BUILD-WAVE4-AREAS.md](build/production/BUILD-WAVE4-AREAS.md) lists what was touched).

- **Behaviour changes operators will notice.** (1) Every API route runs per-workspace admission (429 or 503 with `Retry-After`) and dispatch is refused BEFORE the operation is claimed when a workspace is over its dispatch rate or active-operation quota or the operator has paused dispatch; defaults are generous, every knob is an environment variable ([CONTROL-PLANE-FAIRNESS.md](platform/operations/CONTROL-PLANE-FAIRNESS.md)). (2) The platform migrator now refuses a pending migration that is not expand-only on Postgres (or with `ZENITH_ENFORCE_EXPAND_ONLY=1`). (3) A destroy review taken before this build for a teardown that deletes non-AWS DNS records has no ownership proof and is refused at apply: redo the review. (4) The ECS image pointer SSM parameter moved to `/zenith<NameSuffix>/image-pointer/...` (see the next item). (5) Worker start-up refuses shared key material between key purposes and a release private key on the control plane. (6) `scoped_guest` Kubernetes connections can carry a deployer part; without it deploy and observe are refused with `deployer_credential_refused`. (7) Verified contracts changed on purpose: the Azure deploy audience regex, Azure role assignments (`skip_service_principal_aad_check`), stricter ACR host detection, the OCI runner allowlist (Go sizes 58/58/11, hand-edited, to be checked by the generator), the AWS bootstrap policy grants (scoped additions, seven `iam:*Policy*` removals, a CloudFront origin access control exception in the bootstrap test), `vaultCipherFromEnv` (now resolves through the key registry with unchanged messages), `createAesResultSealer` boxes (optional key id), `log.ts` (redacts every string field and stack) and `tests/machines/scoped-guest-session.test.ts` (observe without a deployer part now expects `deployer_credential_refused`).
- **ECS image pointer path moved (LIFE-03).** The SSM parameter that holds the deployed image of a built ECS workload is now `parameter/zenith<NameSuffix>/image-pointer/<environment>/<node>/image` (it was `/zenith/<environment>/<node>/image`) so the deploy role can be granted exactly that prefix. An existing environment keeps reading the old parameter until its next apply or redeploy; that apply creates the new parameter and replaces the old one in state. After the narrowed role is applied it can no longer delete the old path, so the old parameter can be left orphaned (or the delete refused): remove each leftover `/zenith/<environment>/<node>/image` with an administrator credential once the environment runs from the new path (`aws ssm delete-parameter --name ...`). The verifier should compare the plan for an existing environment before approving it.
- **AWS least privilege (LIFE-03).** Partition, service-principal and per-resource-limit handling is contract-level only for `aws-us-gov` and `aws-cn`; isolated partitions (`us-iso*`) refuse. The static role policies cannot auto-split beyond hosted zones (the generator refuses with a split plan), the CloudFormation template cannot overflow zones (IAM refuses), and the five OIDC provider actions stay denied by design. OpenTofu changes (`main.tf`, `variables.tf`, new tofu test runs) were not executed. CloudFront origin access controls have no tag or name scoping (documented exception). Live IAM acceptance (`tests/acceptance/aws-iam-live.test.ts`) is deferred and skips by design.
- **Azure sovereign clouds (LIFE-04).** `usgov` and `china` are contract-level only: ARM, Entra, Key Vault, ACR, Blob and DNS zone names come from published tables and are unverified live; the customer must also configure the per-cloud `azurerm` provider environment in their bootstrap block (`deploy/azure/README.md`); private endpoint zones for Key Vault and ACR exist in the cloud table but no driver creates those endpoints yet; ACR digest evidence for sovereign registries relies on the preview `outputImages` shape; live acceptance for Azure was not run (`scripts/acceptance/azure-live.ts` is gated).
- **OCI deletion evidence and non-AWS DNS teardown (LIFE-05, LIFE-06).** OCI work-request receipts are journal-only by-id reads, listing is used for other families, and there is no work-request evidence for Core, DNS, load balancers, certificates, vault, identity or Object Storage; MySQL keeps its earlier limits. Non-AWS DNS teardown (GCP Cloud DNS, Azure DNS including the companion TXT, OCI DNS) now proceeds only with a reviewed ownership proof bound to the approval and recomputed at apply; unreadable, foreign, unmapped or changed records refuse and an `already_absent` readback is accepted idempotently. This replaces the earlier blanket refusal. Live cloud verification is unperformed ([TEARDOWN.md](platform/operations/TEARDOWN.md)).
- **Actual spend and costs (COST-01, COST-02).** The bundled catalog `2026-10-05.2` was NOT refreshed: no tiers, inter-AZ, storage I/O or cross-region backup copy prices, so egress is first-tier-only and the extended dimensions refuse when usage is supplied. The normalizer rules were tested against hand-built fixtures in the documented file shapes, not live files; GCP, Azure and OCI compute and database SKUs have no rule. Actual-spend adapters (AWS Cost Explorer, GCP BigQuery export, Azure Cost Management, OCI Usage) ran only against recorded responses; the SigV4 test vector in `tests/cost/billing.test.ts` must be checked against AWS's published vectors. Billing credentials come from an operator-supplied FILE, not the credential broker; refresh is POST, browser-session only, not admin-gated, with no scheduled collector. Forecast is a run rate (floor plus observed daily average) without credits, refunds or billing lag. The extended usage fields are accepted by the REST schema but not by the MCP `zenith_recommend_placement` input (its pinned schema digest would change). No page reads actual spend yet.
- **Fairness and observability (OPS-02).** Fairness inside Temporal is a bounded delay at the worker plus the dispatch quota; it does not reorder tasks already in the Temporal server queue, and per-tenant task-queue partitioning was designed out for rollout safety. Operation-bound runner jobs are not refused at the tenant queue cap (a mid-operation refusal would end a mutating step uncertain); they are bounded by the active-operation quota and a hard ceiling. Reconcile auto-repair, scheduled runbooks and cron ticks are not paused by dispatch pause (they are the drain's recovery path). The edge shield cannot read the database: stored read-only maintenance is enforced in `route()` and at dispatch, the edge enforces only the host override; MCP, waitlist and signed agent endpoints are outside `route()`. Limiter state is per process. Nothing was imported into Grafana, Prometheus or an OTel collector, there was no Temporal-backed fairness run and no staging rehearsal of read-only maintenance or a control-store outage; the `ZENITH_TEST_OPS_EXCLUSIVE_PG=1` maintenance-row cases need an exclusively owned database.
- **Rolling upgrades (OPS-03).** Workflow-history replay fixtures are not recorded: the verifier runs `npm run replay:record` first, commits `tests/fixtures/workflow-histories`, runs `npm run replay:check` and only then adds the replay lane to the gate manifest (it is not part of the mandatory CI lanes). Worker Deployment version routing (`ZENITH_WORKER_VERSIONING`) is untested against a real server and off by default; rolling a worker back across a patch is unsafe without `pinned`; the Kubernetes manifests carry placeholder digests and the runbook is never applied to a cluster; the compat baseline must be set per release; the expand-only classifier is text analysis (an unrecognised statement is refused). The MCP protocol was audited, not changed; the runner and machine windows are v1-only, so N-1 behaviour is proven with synthetic windows.
- **Key custody and sensitive persistence (OPS-05, OPS-06).** Redaction and write guards recognise shapes only: a secret with no recognisable shape sent to events, evidence, log fields, free-text stores or model results is stored or returned (pinned by characterization tests); the only protection for such a secret is not sending it there. Legacy product tables, hosted app records and agent operation documents are inventoried from their migrations only (`unreviewed`, ratcheted) and protected by access control. Every wave-3 and wave-4 table is classified in `src/lib/sensitivedata/inventory.ts`, including `mcp_stream_events.payload` and `coding_agent_runs.checkpoint` (model and tool content stored as given). Effect receipts keep a sealed copy of every outcome until retention policy (PROD-OPS-07) decides; removing a result key makes old receipts unreadable. Backups, agent-link and invite sealing have no decrypt-only overlap; plan custody rewrap is not implemented (`key_rewrap_jobs.purpose` is vault only); key ages come from first sight, not generation time, and there is no HSM or enforced rotation deadline. **DEC-RETENTION is pending: `data-minimize` is a dry run unless `ZENITH_DATA_MINIMIZE_APPLY=1` and an explicit `ZENITH_RESULT_RETENTION_HOURS` are set.** The re-wrap covers vault rows on the Postgres product store; the file store needs the quiesced `scripts/vault-rewrap.ts`; Temporal history cannot be re-wrapped. No key-rotation drill ran against a real Temporal namespace or KMS.
- **Kubernetes deployer part (K8S-CONN).** A `scoped_guest` connection serves guests through its namespaced minter and serves deploy and observe only when it also carries a separate deployer credential (`deployerCredentialRef`, declared `namespaced` or `cluster`, verified with the minter and revoked together with it); without a deployer part deploy and observe are refused, and neither credential ever stands in for the other. The deployer is customer-held (Zenith cannot delete it cluster-side), its verification probes a small verb set (get serviceaccounts, list pods, get and patch deployments per namespace) and the namespaced declaration is trusted via SelfSubjectAccessReview probes, not an exhaustive RBAC audit; a deployer lacking the StatefulSet, CronJob, PVC, NetworkPolicy or Job verbs verifies and then fails at apply with the provider's own error. Same-identity detection compares resolved vault values, so two tokens of one ServiceAccount are not detected as one identity. A connection created before this change has no deployer part: add one with `connection.rotate`. The CLI create handoff now tells the operator that a deployer part is a separate credential; the `kind` test is skipped without `ZENITH_TEST_KIND=1` and is never a pass.
- **Mixed-provider plans (MIX-01 to MIX-04).** A mixed parent runs its children one at a time through `mixedParentWorkflow`; children are separate operation workflows claimed through the broker and the durable start intent and observed by long-poll activities (not Temporal `executeChild`), each under its own approval and guard chain, and a claimed child whose start cannot be confirmed ends the parent `uncertain`. The run service records every child transition, ordering, timeout (24 hours), cancellation and expiry (the parent approval's expiry stops NEW starts), and never claims atomicity, rolls back or compensates; teardown is a human-approved proposal per step with ownership evidence from the resource registry (it proves "Zenith-managed here", not which operation created a resource). A changed parent digest after outputs materialize opens a review operation binding exactly that digest and the original child set (a separate human approval; a policy allow without a person never counts) or is covered by a precise live preauthorization; it never rebinds on its own. **The platform has no producer output reader yet** (`MixedWorld.childTypedOutputs` is not wired), and the compiler does not consume references (`compilerReferenceCoverage` is `unavailable`), so a plan with cross-partition references stays refused at start (`outputs_unavailable`), drift and migration observations are not fed into the ordering rules (`NO_SIGNALS`), and OCI cannot be a child through the product store (it is not a product provider). A child that outlives a cancelled parent keeps running under its own workflow; the sweep ticks runs but nothing re-observes it. A preauthorization use is spent when reserved and is not returned if the next write fails. There is no UI for preauthorization digests or for actual spend, REST only. Live multi-cloud acceptance (`ZENITH_LIVE_MIXED=1`) was not performed.

## Production wave 3 (7 October 2026, implementation complete, verification pending)

Wave 3 added PROD-DUR-01 to DUR-08, OBS-01, MACH-02, MACH-06, UX-02 and LIFE-07, plus gap fixes for OBS-02 and LIFE-11, on top of waves 1 and 2. Nothing below has been executed on a test machine: no vitest, go test, Docker, PostgreSQL, Temporal, kind or cloud run has covered these bytes. Per-requirement detail lives in `docs/build/production/verify/` ([VERIFY-QUEUE.md](build/production/VERIFY-QUEUE.md) has the ordered runbook).

- **Behaviour changes operators will notice.** (1) New Kubernetes connections default to `scoped_guest`; legacy `kubeconfig_ref` connections keep deploy and observe but their guest (machine) sessions are refused until converted with `connection.rotate` `convertToScopedGuest`; a `scoped_guest` connection serves guests through its namespaced minter and serves deploy and observe only when it also carries a separate deployer credential (`deployerCredentialRef`, declared `namespaced` or `cluster`, verified with the minter and revoked together with it); without a deployer part deploy and observe are refused, and neither credential ever stands in for the other (wave 4, K8S-CONN). (2) The OpenTofu backend compile refuses backends that cannot lock state or do not encrypt it. (3) A plan reviewed before this build carries no executable-semantics record and is refused at dispatch (plan again). (4) Worker plan-artifact operations are refused with `plan_custody_refused` without a valid worker identity and live lease. (5) Coding-agent runs need `ANTHROPIC_API_KEY` (optional for everything else; `model_not_configured` otherwise). (6) The Navigator default model id is `claude-opus-5-5`. (7) Two kind tests changed meaning with MACH-02 (empty-namespace and the 401 revocation expectation) and two LIFE-11 MySQL tests were edited because DNS-host TLS is now served instead of refused.
- **Durable intent and authority (DUR-01/02).** A start whose process dies after a runner claim but before its intent is prepared still ends as explicit `uncertain`, not a recovered start. Relay resend is bounded to 30 minutes and a live lease; past that an operator inspects the intent (no operator-authorized continuation or recovery epoch). Provider HTTP proxy runner jobs (`aws.http`, `oci.http`, `k8s.http`) are not keyed by the intent layer; the external-effect ledger (DUR-07/08) records every mutating proxy request instead. Simulator-engine deployments have no platform operation and are still decided from the product store. Product projection repair is best effort.
- **Executable semantics (DUR-03/04).** The digest binds revision, recipe, scripts, migrations, targets, configuration, provider locks, backend, saved plan, provenance, ownership transfers, the signed runbook version and adoption claims. The migration class is the declared class (`sqlDigest` stays null until SQL is available to classify). The runbook component binds only operations whose input carries a runbook reference; nothing in the product emits that field yet. Build provenance is produced after approval and is verified against the recipe at admission (LIFE-09). Standing grants are REST plus an admin page, are not shown in the MCP operation view, spend their use count at proposal, and never cover destroy. A provider-direct teardown binding has no dedicated test, and the standing-grants page has no component test.
- **Plan custody and state recovery (DUR-05/06).** Custody binds authorization and audit to a worker identity; it does not stop a process that holds `ZENITH_PLAN_ARTIFACT_KEY` from decrypting an artifact it can read, and there is no per-worker key re-wrap (KMS or HSM). `revokeWorker` reaches only workers that already hold grants. Restore is AWS S3 and GCS only, through the capability broker; Azure Blob, OCI Object Storage, http, local and pg are refused. A restore grant is an in-process grant with a synthetic correlation id (no operation row, no `state.restore` capability in the catalog). Restore is REST and browser only (no MCP tool, no UI page). Proposal expiry by clock has no timed test. Physical retention and pruning of artifacts or state versions is not implemented.
- **External effects (DUR-07/08).** Independent readback exists for AWS, GCP and Azure build launches and for destroy apply (from reconcile observations newer than the dispatch). Kubernetes and OCI have no build path; mutating proxy requests have a readback hint only, so a lost one stays uncertain. Absence is evidence, not quiescence (15 minute settle window plus a gone fence). The operation status column is not rewritten by effect state: the journey, UI and effects API show it, MCP `get_operation` and the CLI do not yet. Identical mutating proxy requests within one operation are deduplicated by request digest, which could suppress a legitimate repeated mutation; the verifier must check this. Late agent receipts keep their own table. Real CodeBuild, real GCP and Azure readback and the Temporal retry path are unexercised.
- **Repair lifecycle (OBS-01).** One lifecycle door serves the Temporal pass, the HTTP tick and the durable sweep; the reconcile workflow pass result now reports `not_evaluated` where it previously diverged, so histories need a replay-determinism check. Verification is recomputed on every pass for open incidents (no verified marker); a repair whose node is not observable stays `unverifiable`. Remediation dispatch reaches execution only through the broker `beginExecution`, which re-authorizes at dispatch (DUR-04). Live provider remediation and ECS adapter acceptance are not claimed.
- **Kubernetes guest credentials (MACH-02).** The minter is trusted to be namespaced by six denied SelfSubjectAccessReview probes plus create, get, update and delete checks; this is not an exhaustive RBAC audit. Already-issued tokens die when the ServiceAccount is deleted or at expiry (at most 15 minutes); a cluster outage during revoke leaves bindings `revoking` (unmintable) until revoke is repeated; there is no scheduled retry. `pods/exec` lists `get` and `create` for older API servers. LIFE-07 StatefulSet and CronJob pods are reached through the same namespace-wide pod verbs; no per-workload narrowing exists. The deployer part added at wave 4 is customer-held (Zenith cannot delete it cluster-side), its verification probes a small verb set and the namespaced declaration is trusted via SelfSubjectAccessReview probes, not an exhaustive RBAC audit.
- **Kubernetes lifecycle (LIFE-07).** Snapshots are crash-consistent and attempted only where CRDs, a CSI-backed claim and a matching VolumeSnapshotClass exist (otherwise `snapshots_unsupported`); restore never overwrites; StatefulSet rollback never restores volumes; raw PVC data still has no mover for LIFE-11; NetworkPolicy enforcement is a cluster property proven only by the traffic test; managed-cluster runs are deferred (kind plus Calico only). The Kubernetes build port still refuses source builds.
- **Coding agents (MACH-06).** Live model behaviour (injection resistance, output budget under the 8000 per-call cap) is unverified until the key-gated live eval is run; a skipped eval is not a pass. Spend is an upper estimate from a fixed price table. A stale running row (no step for 10 minutes) can be resumed from the UI or API. The proposal needs a human-chosen target and its principal is the signed-in admin. There is no recorded replay history for the new workflow type yet. The UI was checked by convention tests only.
- **Client interoperability (UX-02).** The official MCP SDK client (`@modelcontextprotocol/client`) is not installed, so `--official` in `agent:conformance` is an unexecuted optional leg; the verifier uses real Claude Code and Codex per `docs/platform/CLIENT-INTEROP.md`. Zenith hosts no authorization server. Resume depends on the running instance staying alive up to 55 seconds; non-streamed cancellation reaches only the instance holding the call; modern (2026) requests have no resumable ids. Several SDK 2.0.0 behaviours were read from source, never executed.
- **OBS-02 composition (gap fix).** Prometheus and Loki endpoints are platform wide operator configuration (`ZENITH_OBSERVE_*`), not per workspace. Machine health envelopes are stored as `machine_health` observation evidence, not appended to the activity result.
- **Portability MySQL by hostname (LIFE-11 gap fix).** The in-process transport dumps with `DEFINER` stripped, no `DROP` statements and no routines or events, and is not byte-identical to `mysqldump`; it restores with both the stock client and the in-process restore. MariaDB was not considered; exotic types (GEOMETRY, JSON) are the likeliest digest mismatch against the stock client. One connection per call. The wire fixture is a hand-built MySQL protocol subset, so a fixture mismatch with mysql2 is the first suspect when its tests fail. The previous refusal of DNS-host TLS is gone; the real-server lane is `ZENITH_TEST_MYSQL_DNS_TLS_URL`. The removed sub-case in the gated real-server test of `mysql-engine.test.ts` and the edited `mysql-cli-tls.test.ts` expectations need a reviewer's confirmation that nothing was weakened.
- **Generated artefacts.** `supabase/migrations/0023_platform_core.sql` (migrations 1 to 41) is generated; `0016` to `0022` are immutable. A database that applied only `0022` is behind and must apply `0023` or run `npm run migrate:platform`.
## Production wave 2 (5 October 2026, implementation complete, verification pending)

Wave 2 added PROD-OBS-04, LIFE-01, LIFE-08, LIFE-09, LIFE-10, LIFE-11, MACH-04, MACH-05, UX-01 and UX-03 on top of wave 1. Nothing below has been executed on a test machine: no vitest, go test, Docker, PostgreSQL, Temporal or cloud run has covered these bytes. Wave 1 must be verified first ([VERIFY-QUEUE.md](build/production/VERIFY-QUEUE.md)). Per-requirement detail lives in `docs/build/production/verify/PROD-<ID>.md`.

- **Behaviour changes operators will notice.** (1) Source builds with unrestricted egress are refused unless `ZENITH_BUILD_ALLOW_OPEN_EGRESS=1` (recorded on the signed statement) or the pipeline is re-applied with the guarded AWS buildspec or a private GCP pool / Azure agent pool; AWS projects created before this change report `unrestricted` until re-applied. (2) Every managed workload needs a sha256-pinned image: a mutable tag is refused (`ZENITH_RELEASE_MIN_PROVENANCE`, default `pinned_digest`). (3) An image Zenith builds from source is released only with admitted signed build provenance, which the release gate records as `attested`, whatever the floor. (4) A subdirectory build context needs the digest source inspection returned, re-derived from the approved commit; without it, or on a worker with no GitHub access port, the build is refused. (5) MCP redaction now emits `[REDACTED:<kind>]` instead of `[redacted]`.
- **One provenance path, one trust statement (LIFE-09/10).** The attestor is the control plane (`zenith-control-plane-observed`): it signs facts read back from the provider after the build; the cloud builder does not co-sign. The signature protects the stored record and binds it to operation, service, digest and reviewed source; it does not make a compromised provider API truthful. Pinned (not built) images are `pinned_digest`: Zenith knows the digest, nothing about its origin.
- **Build isolation limits (LIFE-09).** AWS egress allowlist is IP based, resolved once per build (shared CDNs admit neighbours), DNS stays open (covert channel), BuildKit insecure entitlements would bypass FORWARD rules, and metadata blocking covers forwarded Dockerfile traffic only (the buildspec's own commands and static-site builds still see the build role). GCP and Azure metadata endpoints cannot be removed; the profile accepts only the per-pipeline build identity. Azure cannot build from a context subdirectory and does not return its timeout; the Azure helper `runAcrBuild` still requests 3600 s but is off the release path. OCI and Kubernetes keep refusing source builds; buildpack plans are refused (no isolated buildpack builder). No live cloud evidence: contract classes only.
- **Release pipeline (LIFE-10).** A migration awaiting approval does not pause the workflow: the person approves release `rel_...` in the browser, then deploys again. Progressive rollout exists for Cloud Run only; readback for Cloud Run and Kubernetes only (AWS, Azure, OCI end `cut_over_unverified`). Migrations run after the deploy step. The legacy in-process engine rollback is not covered. Provider code is contract-tested against synthetic REST.
- **Connections (LIFE-01).** OCI is not a product `ProviderId`, so an OCI connection exists only as a platform record. Runner-mode connections cannot be created or verified. Revoking cannot end provider sessions already minted (up to 15 minutes) or remove customer trust. AWS ExternalId rotation is zero-downtime only if the operator lists both ExternalIds in the trust policy. CLI create/rotate/promote/abort stay browser-only. Route handlers have no direct test.
- **GitHub source (LIFE-08).** One binding per workspace; unsuspend requires an explicit re-bind; buildpack plans are detected but not buildable; inspection is static only. No live GitHub App evidence.
- **Portability (LIFE-11).** MySQL is contract-level only; live managed databases (TLS chains, IAM auth, VPC reach) are unverified; Kubernetes PVC data has no mover and is refused; exports are held in memory with hard caps and are not encrypted by Zenith; DNS rebinding between host check and connect is not closed; `resource.release` flips stored ownership only; no UI page.
- **Machines and runners (MACH-04/05).** Updates are unverified on real systemd (exec launcher, exit 75/76, `noexec` state mounts, `ProtectSystem=strict`); a control-plane outage covering the whole `healthWindowSec` rolls a good release back; there is no control-plane-initiated update or hold. Go spool replay test depends on timing (2 s initial delay, up to 30 s drain).
