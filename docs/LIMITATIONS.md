# Known limitations (kept honest, updated at each phase)

Status legend: ✅ implemented · 🟡 partial · ⬜ not yet built

## Platform
- ✅ Canonical manifest, diffing/changesets, cost model, validation
- ✅ Typed action registry with plan/execute/audit/idempotency + autonomy enforcement
- ✅ Durable JSON/JSONL store (single-process ceiling by design; SQL swap is contained to `src/lib/db`). Split hot from cold: `state.json` holds revision *metadata* and is rewritten on every save; revision manifests live one file each under `<ORRERY_DATA>/revisions/` and load on demand. A 500-revision store serialises 110 KB per save instead of 1.13 MB (−90%), 5.4 ms instead of 20.7 ms — measured, `tests/db/bench-manifests.ts`. Pre-split snapshots migrate on first load. Metadata still grows linearly with deploys, and the whole snapshot is still rewritten per save: the ceiling moved, it did not go away
- 🟡 **Live updates are in-process only.** Every save emits a change event and `GET /api/projects/:id/stream` pushes the project payload from it, so an open project screen no longer polls every 5s. The emitter is an `EventEmitter` on `globalThis`, not a message bus — a second server process would emit to nobody, exactly like the store's single-writer ceiling. Every screen keeps the poll behind the stream and falls back to it automatically (no `EventSource`, an errored connection, or one that opened and never delivered), so the degradation is a slower refresh, never a frozen screen. Deployment, log and alert streams are unchanged: they still tail their own logs on a 300ms poll
- 🟡 Multi-tenancy: optional Supabase auth (email/password, confirmation, reset; `/login`, `/signup`) gives real identity, and actions/audit carry the signed-in user; without keys it is still one local demo user. OAuth sign-in (GitHub, Google) is wired through the same `/auth/callback` and the same membership rule, but is shown only for providers named in `NEXT_PUBLIC_SUPABASE_OAUTH_PROVIDERS` *and* enabled in the Supabase dashboard — unset means no buttons at all, and the handshake itself has never been exercised in this repo (verified by code reading and unit tests, not by a real round trip to a provider). **Multiple workspaces per install**, one *current* workspace per user: `POST /api/workspace/select` writes an httpOnly `orrery-workspace` cookie after checking membership, and `requireWorkspace()` re-checks membership on every read, so a stale cookie is ignored rather than obeyed (cookie → the caller's first membership → demo `workspaces[0]` → 404 naming `/onboarding`). `POST /api/workspace` creates another one, makes the caller its admin and selects it; **demo mode stays single-workspace** and says why — with one local user who is admin of everything, a second workspace is only a second name for the same permissions. Joining requires an invite to *that* workspace, an operator-set `app_metadata.role`, or being *that* workspace's first real member: being admin of A grants nothing in B, and an invite to B never makes you the first-member admin of an empty A. Still **one process and one data directory** — workspaces are rows in the same JSON snapshot, not separate stores, so the single-writer ceiling in `src/lib/db` applies to all of them together. `requiredRole` is enforced on execute against the member's role (planning stays open). The Navigator's own steps run as the Navigator actor, so `runAction` never role-checks a human there — the executor separately refuses a run whose steps outrank the person who pressed Run. The `x-orrery-actor` binding covers only the HTTP `/api` surface: server actions never carry those headers, so the in-process Navigator path is trusted because it is in-process, not because it is bound
- ⬜ `roleOf` (`src/lib/actions/core.ts`) still finds a member row by id across every workspace, so for a user who belongs to two it answers with whichever row sorts first. Membership routes are unaffected — `requireAdmin` uses `workspaceRole()`, which scopes to the resolved workspace — but `runAction`'s own `requiredRole` check does not, so a user who is admin of A and viewer of B is role-checked as admin in B. The fix is to pass `ctx.workspaceId` into `roleOf`
- ⬜ Real network security, rate limiting, encryption at rest for the snapshot and the logs (the secret store is encrypted; see below)
- 🟡 **Container support ships but is one container, not a deployment.** `Dockerfile` (multi-stage, Next `output: "standalone"`, non-root) and `docker-compose.yml` (LocalStack + app, `app` profile, healthchecks, named volumes) run the whole thing with `docker compose --profile app up` — see `docs/RUNNING.md`. Three ceilings, all inherited rather than introduced: the store's single-writer rule means **`replicas: 2` silently destroys data**, so this scales to exactly one app container per `/data` volume and `data-lock`'s pid file cannot even detect the second one (different pid namespaces, same directory); the image build needs egress to `fonts.googleapis.com` because `layout.tsx` uses `next/font/google`, so an air-gapped build fails on fonts rather than on code; and `NEXT_PUBLIC_*` are inlined at build time, so changing Supabase keys is a rebuild, not a restart. No Kubernetes manifests, no published image, and the container image itself is **written against Next's standalone example but not yet built on this machine** (Docker Desktop here is in the stale-socket failure state documented in `RUNNING.md`) — CI's `docker` job builds it on every push, `continue-on-error` like `build`

## Secrets
- ✅ **Real:** a per-workspace store at `<ORRERY_DATA>/secrets.json`, values encrypted with AES-256-GCM under `ORRERY_SECRET_KEY` (32 bytes from the environment), workspace + reference authenticated with the ciphertext. The manifest holds only `vault:<KEY>`, so no value reaches a diff, a revision, the audit log, the project payload the browser loads, or an export bundle. `system.setSecret` / `system.rotateSecret` / `system.removeSecret` are plan-first and editor-only; the security report's "Move to the secret store" fix moves a plaintext value in one action, writing the store before it commits the manifest so a failure never destroys the value
- 🟡 **Partial:** the sandbox resolves references at deploy time and logs which version it found, but starts no container, so nothing actually receives a value — the log line says so. A reference with nothing stored behind it is reported in the deploy log, not by manifest validation (which is pure and runs in the browser, and cannot read a server file)
- ⬜ **Not real:** no KMS, no HSM, no envelope encryption — one key for the whole server, held in its environment. No per-user or per-project access control: any editor in the workspace can rotate or remove any of its secrets. No versioned history (a rotation replaces the old value; it is not recoverable), no key rotation tooling (values written under an old `ORRERY_SECRET_KEY` cannot be read back, and there is no re-wrap command), no audit of *reads*, and no export of values in any form — moving to a provider means putting the values into SSM/Secrets Manager yourself, which the Terraform bundle's README shows how to do. LocalStack does not write SSM parameters: the adapter has no SSM client and Orrery will not add a dependency to emulate a store it already has

## Providers
- ✅ Sandbox: full simulated execution, honest labeling, chaos/failure injection
- 🟡 AWS Preview: real plan shapes + real Terraform export; **no real cloud apply** (requires credentials; deliberately disabled)
- ✅ LocalStack: AWS-shaped local testing; selectable in onboarding and Settings, driven by registry availability
- ⬜ Kubernetes, GCP, Azure (Planned; not selectable, and refused at plan time before any revision is written)
- ⬜ Customer-side runner / short-lived workload identity (designed in docs, not implemented)

## Import & migration
- 🟡 Docker Compose / Dockerfile import with explained mapping report; all three importers are reachable from onboarding and the map's import dialog
- 🟡 Terraform import: reference-level resource detection only, labeled preview
- 🟡 **Live cloud-resource discovery, per provider.** LocalStack is real: `discover()` lists the buckets and queues actually present at the edge endpoint. The sandbox invents a small, stable set, labelled simulated in the dialog and prefixed `sim://` in every reference it writes, so an imported row stays recognisable as a simulation long after the dialog closes. AWS Preview refuses — no code path reads your account. Everything imported is **`referenced` only**: Orrery draws it on the map and lets services bind to it, but never provisions, changes or deletes it, and it adds nothing to the cost estimate. There is no path from discovery to `managed`, so adoption cannot become ownership by accident
- ⬜ Discovery covers object stores and queues only (the kinds LocalStack Community actually emulates). No VPC/IAM/networking discovery, and no reverse-engineering of bindings: Orrery learns that a bucket exists, not who talks to it — you draw that edge yourself

## Drift
- ✅ Drift is computed as the deployed revision vs. what the provider's `observe()` finds: `missing`, `changed` and `extra` items with a severity, on the Observe screen and as a chip on the affected map nodes. Read-only end to end — no store write, no audit row, no cached answer
- ✅ **Real for LocalStack.** A bucket or queue deleted out from under Orrery is reported missing, and anything at the endpoint this environment does not own is reported as extra. That is a genuine reading of a genuine endpoint
- 🟡 **Simulated for the sandbox**, and labelled simulated everywhere it appears. The sandbox reports every managed node present with exactly the attributes the revision asks for, then introduces two seeded differences — one resource a size up, one plain env var altered — so the screen has something true-to-shape to show. It is a demonstration of what drift looks like, not a measurement, and it is deterministic: the same environment drifts the same way on every poll
- ⬜ **Absent for AWS Preview**, and it says so rather than showing an empty list. Orrery reads no AWS account, so it cannot report drift and will not invent it; the refusal names `terraform plan` against the exported bundle as the way to see real drift today
- ⬜ No remediation: drift is reported, never reconciled. There is no "fix drift" action — deploying the environment again is what puts it back, and the copy says so
- ⬜ LocalStack drift is `missing`/`extra` only. Nothing it can cheaply read back (a bucket's creation date, a queue's URL) corresponds to a field the manifest specifies, so `changed` never fires there. Attribute-level drift on a real provider needs per-kind attribute mapping that does not exist yet
- ⬜ "Unowned" means unowned *by this environment*: two Orrery environments sharing one LocalStack each report the other's buckets as extra. Scoping the owned-set across a workspace is noted in `src/lib/providers/localstack/index.ts`
- ⬜ Nothing alerts on drift. It is visible when a screen is open, on a one-minute poll that backs off further while the answer keeps coming back the same — see the alert-delivery gap above, which applies here too

## Operations
- ✅ Deploy plan → apply → streamed progress → activation URL → revisions → rollback (sandbox)
- 🟡 Logs/health/cost are sandbox-synthetic (honest: generated, labeled simulated); the sandbox replays only its last 200 log lines on connect, and search, filter and download operate on what is loaded
- ✅ Alert rules are real: four conditions (`health_degraded`, `deploy_failed`, `budget_exceeded`, `replicas_below`) per environment, evaluated every 15s from boot and again whenever the Alerts panel is read, deduplicated to one open event per rule, resolved when the condition clears, acknowledged by an editor, and recorded durably — the record outlives the rule that produced it. Conditions read the same inputs the screens do, so an alert can never disagree with the health card above it, and every event carries `simulated` (true for health-, replica- and cost-derived conditions, and for a sandbox deploy failure)
- ✅ **Alert delivery is real for webhook and Slack.** Per-workspace channels under Settings → Alerts (`db().settings.alertChannels`, admin to create/edit/delete, editor to test). A webhook is a real `POST` of JSON, signed with HMAC-SHA256 in `X-Orrery-Signature` over the exact body when the channel has a secret; Slack is the real incoming-webhook payload (text + blocks). Every fire **and** every close is pushed — including a close caused by disabling or deleting the rule, so a receiver never keeps a stuck open alert. Three attempts with backoff, 10s per attempt, and the outcome of each channel is recorded on the event (`AlertEvent.deliveries`) and stamped on the channel (`lastDelivery`): a failure is a row with the reason and the fix, never a silent drop. Delivery runs off a microtask queue after the evaluator saves, so it never blocks or delays evaluation. A rule delivers to every enabled channel unless `channelIds` names some (`[]` = deliberately on-screen only)
- 🟡 **Email delivery needs SMTP configured on this server.** `ORRERY_SMTP_URL` (which carries the password, so it is never echoed) plus `ORRERY_ALERT_FROM`, and the `nodemailer` package installed. Missing any of those is reported as the delivery failure, naming the variable or `npm install` — nothing is silently dropped, and webhook and Slack channels are unaffected. One recipient address per channel; no HTML body, no templates, no per-recipient preferences
- ⬜ **No paging and no on-call.** No PagerDuty/Opsgenie, no SMS, no push, no escalation, no rotation, no repeat-until-acknowledged, no quiet hours, no per-rule routing by severity. A channel that is down when an alert fires misses it: after three attempts the failure is recorded and not retried later, and there is no dead-letter queue — the operator sees the failed delivery on the alert and presses Test once the endpoint is back. Credentials (a webhook signing secret, a Slack webhook URL) are held in plain text in `<ORRERY_DATA>/state.json`, masked everywhere Orrery shows them but readable by anyone who can read that file
- ⬜ Real metrics ingestion; alert conditions beyond the four above (no per-rule schedule, no "for N consecutive checks" hysteresis, so a condition that flaps faster than 15s produces one event per flap)
