# GitHub source revocation webhooks

This source candidate wires signed POST transport at `/api/platform/v1/github/webhook`, migrations 9 and 10, exact middleware admission, and revoked-aware browser/store/runtime behavior. Independent review and exact-source runtime gates remain required before publication or endpoint enablement. Prepared contracts do not prove a live GitHub installation.

GitHub signs the original body with HMAC SHA256 in `X-Hub-Signature-256`. The transport bounds the original bytes to 1 MiB, allows eight seconds to read them, verifies the signature with `timingSafeEqual`, then parses JSON and opens the control database. It rejects invalid UTF8, duplicate JSON keys, ambiguous headers, malformed identifiers, body length mismatches and encoded bodies. No URL or repository name in the webhook becomes a request destination or authority selector. [GitHub signature documentation](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries).

Configure the GitHub App with a high entropy webhook secret and an HTTPS webhook URL. Set `ZENITH_GITHUB_APP_ID` and `ZENITH_GITHUB_APP_WEBHOOK_SECRET_FILE`; the environment holds the canonical absolute file path, never the secret value. The file must contain 32–4096 printable ASCII bytes exactly, without a newline. It must be a regular file owned by the service UID, mode `0400` or `0600`, with one hardlink, inside a service-owned `0700` directory. Symlinks, unsafe writable ancestors and changed file identities are refused. A root-owned sticky temporary ancestor is permitted; the immediate parent remains private. Mount a private regular file or make an operator-owned private copy of a symlink-based secret projection. The secret is read afresh and erased from the local buffer after verification; neither it nor the signature is stored or reported.

Accepted revocations are `installation.deleted`, `installation.suspend`, and `installation_repositories.removed`. The configured App ID must equal the signed `installation.app_id`; installation and removed repository IDs must be positive safe integers. Installation revocation selects matching App and installation IDs across workspaces. Repository removal additionally selects only the exact removed repository IDs. The schemas confirm the action is `suspend`, rather than `suspended`. [GitHub events](https://docs.github.com/en/webhooks/webhook-events-and-payloads#installation), [primary suspension schema](https://github.com/octokit/webhooks/blob/main/payload-schemas/api.github.com/installation/suspend.schema.json), [primary repository removal schema](https://github.com/octokit/webhooks/blob/main/payload-schemas/api.github.com/installation_repositories/removed.schema.json).

An authenticated `ping`, `created`, `unsuspend`, `new_permissions_accepted` or repository `added` delivery is acknowledged without opening SQL or granting access. Other events/actions are refused. Both installation event families are delivered automatically to GitHub Apps. Operators must arrange redelivery after a refusal or outage; GitHub does not automatically retry failed deliveries. Oversized or unsupported events require a deliberate operator response. [GitHub delivery guidance](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks), [failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries).

Each accepted revocation commits one transaction containing a delivery receipt, installation generation advance, active binding version increments, revocation timestamps, fixed `github_webhook` audit actor, and pending intent invalidation. Existing binding rows and versions are retained. Already-revoked bindings stay revoked. Installation events also cancel known App/installation OAuth intents even when no binding exists. Repository events cancel the affected bound workspaces' intents; their installation generation also invalidates older consumed or first-binding callbacks whose repository authority was not yet verified. No raw body, signature, token, sender name or provider URL enters the receipt.

Only the frozen object authenticated in this process is accepted by the SQL worker. A private runtime WeakSet check refuses caller-created objects, cloned objects and TypeScript casts before starting a transaction; a caller-provided approval flag cannot authorize a revocation.

Receipts retain App ID, delivery GUID, body SHA256, event/action, installation/repository IDs, affected count, replay status and receipt time. Reusing a GUID with a different body or authority metadata returns `409`. The HMAC signs the body, while the GUID is an unsigned header: identical signed bytes with a changed GUID therefore create a replay receipt without another generation/version advance. This conservative digest rule also suppresses a genuinely distinct delivery with byte-identical contents. It prevents an old signed revocation from being reapplied after fresh browser verification restores a binding. No receipt or generation retention/pruning policy is introduced. Success and duplicate responses are `204`; refusals expose only a fixed message.

Lock order is installation epoch row, tenant advisory locks in workspace ID order, then binding rows. PostgreSQL uses `zenith:github-binding:<workspace>`; PGlite serializes through its engine. A mutation with an unknown backend refuses. Browser binding must use this same order and verify the current human after every lock wait.

`captureGithubWebhookFence(dbOrTx, appId, installationId)` returns a canonical nonnegative bigint generation string and locks the installation epoch until the surrounding transaction ends. It must run before external GitHub verification. `assertGithubWebhookFence(tx, expected)` takes the same lock, checks the immutable captured generation, and must run first in the transaction that performs binding CAS and audit. Generations never decrease. Fresh browser verification can restore authority after an earlier event; a callback that predates an intervening event must restart. This covers `expectedVersion=0`, for which no binding row exists to invalidate.

Integration and acceptance status:

- Migrations 9 and 10 are registered after migration 8 and canonical SQL is regenerated. Legacy OAuth intents retain null App/generation fields and refuse consumption; no fabricated generation is assigned.
- Middleware exempts only the exact signed-webhook POST. Every signature refusal precedes platform SQL or browser authority reads; other methods and callback paths retain browser admission.
- Authorization captures App/installation generation before tenant locks. Consumption returns immutable App/generation; binding verifies them before tenant locks and refreshes browser-human admin authority after lock waits. Begin and browser revoke never wait for installation locks while holding tenant locks.
- Revoked-aware source access refuses revoked bindings, removed App configuration and changed bindings after token acquisition. An already-started fetch may finish; revocation cannot retract previously delivered bytes.
- Canonical PostgreSQL gates require all SDK launch authority cases, source-store contracts, consumed-generation bind refusals and observed lock-wait regressions. Historical Temporal build replay and uncertain parallel-build cases remain mandatory. Current-source execution has not yet been performed.
- Fresh admin verification and POST body reads have eight-second cancellation/deadline bounds. A delayed successful identity response cannot invoke the binding mutation after transaction rollback. Real product PostgREST/TLS and signed-browser identity behavior remain independently unverified.

Operator acceptance still requires configured HTTPS ingress, GitHub delivery/redelivery, private acquisition, uninstall/suspension/repository removal, role revocation, and database/runtime outage checks against authorized fixtures. No live GitHub, production TLS, or product PostgREST claim is made. Delivery/generation pruning and destructive retention remain disabled pending approved policy.
