# Observation and repair proposals

Written against branch `codex/production-2026-10-02`, based on canonical reconciliation source `8657abd` (2026-10-02). This guide records source wiring and remaining release blockers; it does not claim live provider remediation acceptance.

Temporal reconciliation, the HTTP tick and the durable sweep all run one lifecycle, `runRepairLifecycle` (`src/lib/repair/lifecycle.ts`): observe, diagnose, brokered proposal, policy, approval, remediate, verify. Every finding that is not repaired carries a typed refusal with a reason (`src/lib/repair/refusals.ts`). A repair that has settled is verified by the next observation: the node read clean (the incident closes by hysteresis), still drifted (escalated to a person as `verification_failed` when the operation had reported success) or unreadable (nothing is claimed; stored facts decide escalation). The controller primitives are `reconcileObserveOnce`, `reconcileEnvironment` and `proposeRepairs`. The worker renews its existing `reconcile:<environmentId>` lease, heartbeats, receives cancellation, and asserts the same fence before persistence, proposals and dispatch. It does not acquire a second reconcile lease. Cancelled or stale passes stop without committing a stale observation or starting another repair.

`allowAutoRepair` permits proposal consideration. It grants no execution authority. A candidate needs a real observation, managed ownership in both graph and store, a safe resource kind, hysteresis/pacing eligibility and either an actual registered `drift.repair` driver handler or admission by the shared pure declarative repair recipe. That recipe admits only the exact managed AWS ECS replica-count finding with a digest-pinned image and bounded desired/observed counts; other fields, providers, ownership and unsupported targets remain refused. Unknown, inaccessible, simulated and external targets cannot become repair proposals. Partial observations retain their unknown/inaccessible provenance; readable safe candidates remain resource-scoped.

The capability broker evaluates each proposal and records allow, approval or denial. Approval remains bound to the immutable proposal digest and a verified human browser session. An allowed operation is claimed through `beginExecution`, which rechecks current policy, scope and approvals, then dispatched to the existing day-two workflow. That workflow retains the environment mutation lease, execution credential grant, policy checks and readback verification. The observation workflow returns only counts and a digest of repair decisions, never provider responses, findings, credentials or arbitrary failure reasons.

An uncertain repair blocks its resource indefinitely. Other unresolved uncertain mutation capabilities conservatively block the environment. A cooldown does not resolve uncertainty. A truncated operation inventory fails closed rather than overlooking an older conflict. Inspect and settle the original operation against authoritative provider and workflow evidence before proposing further mutation. A running or uncertain operation is never blindly dispatched again. A lost dispatch acknowledgement is recorded as uncertain; a failed uncertainty write leaves the running claim blocking another dispatch.

New workflow histories use `patched("reconcile-canonical-proposals-v1")`. The legacy branch preserves its activity request, timeout and two-count result shape; its `repair` field reports `not_evaluated` (the pre-controller pass observed without running the repair lifecycle). The literal `not_implemented` no longer exists in the live result type. Retain the patch until old histories have left retention, following [Temporal's patch lifecycle](https://docs.temporal.io/develop/typescript/workflows/versioning#patching). The dedicated SDK regression records the original definition from commit `83ec97f`, then replays it against the current bundle. A separate isolated Temporal regression exercises the shared controller with the actual control store and broker; provider reads and policy decisions in that fixture are scripted and are not cloud acceptance.

Fresh diagnosis, fleet telemetry, durable observation/reaping schedules, operator settlement and escalation workflows, incident postmortems, and live provider remediation/readback proof remain outstanding PROD-OBS-02/03/04 work. Source regression fixtures and replay preparation are not evidence that production repair or fleet observability is complete.
