The namespace-local identity is `zenith-reconcile-sweep-v1`. Its only action is `reconcileSweepWorkflow` on `zenith-execution`. Every minute it calls one `sweepReconcilePass` activity, which reuses `reconcilePass`; the historical `reconcileEnvironmentWorkflow`, its patch marker, activity policies and replay histories stay unchanged.

The action contains only the contract name and bounded integers. Defaults claim at most 25 environments with concurrency 3. An operator can narrow those to 1..25 and 1..3 when provisioning. A changed configuration refuses adoption and requires a reviewed maintenance change; it is never silently applied. For a small worker, select concurrency 1. The existing database due-time ordering, priorities, claims, deploy nudges, eligibility, per-environment leases, backoff, repair deduplication, uncertainty, approvals, attempt limits and cooldowns remain authoritative. A saturated pass leaves remaining environments due. This retains the controller's current fairness policy; it does not promise equal tenant quotas.

Each pass has a 20-second start budget and a 50-second controller deadline. The activity combines cancellation and a 70-second local signal, heartbeats every five seconds, takes the global `reconcile-sweep:v1` lease for 90 seconds with existing renewal, and releases it in `finally`. This namespace is disjoint from every `reconcile:<environmentId>` lease, including the valid environment ID `sweep-v1`. Our lease/controller SQL uses transaction-local 10-second statement and five-second lock bounds. Activity start-to-close is 90 seconds, schedule-to-close 150 seconds, and workflow run/execution limits are 180 seconds. These limits do not retract an already accepted provider call. Existing broker and credential adapters must honor their own transport deadlines; a database pool wait or an uncooperative adapter can outlive a local abort. Their production deadline checks and lease-loss rehearsal are required integration work, not demonstrated by source configuration.

Both the workflow and activity have one attempt: a pass can dispatch an already broker-approved repair, so a timeout is an unconfirmed outcome and cannot authorize immediate replay. An incomplete pass returns `deferred/pass_unconfirmed` without fabricated zero counts; absent authorization or store prerequisites return `deferred/prerequisites_unavailable`. A genuine completed pass returns only the existing count projection, including partial failures and unread nodes. Cancellation propagates and starts no compensation. The next scheduled observation still checks the existing operation ledger, leases and uncertainty guards before another repair is considered.

The Schedule explicitly uses `SKIP`, a 60-second catchup window, and `pauseOnFailure=false`. It continues minute observation after transient outages. Older missed actions are discarded; manual triggers/backfill are outside this catchup limit and require separate operator authorization. Do not trigger with the SDK's default overlap override; an authorized trigger must explicitly select `ScheduleOverlapPolicy.SKIP`. Temporal documents these semantics in [Schedules](https://docs.temporal.io/schedule) and the [TypeScript Schedule API](https://typescript.temporal.io/api/interfaces/client.ScheduleOptions).

## Provisioning and custody

`createReconcileSweepRuntime` requires an actual PostgreSQL handle and current platform schema. It refuses both memory flags and internally constructs a fresh broker over its owning bounded `PlatformBrokerStore`, platform scope resolver, canonical checksum-verified OPA engine and ready `CredentialGrantSigner`, then composes the existing credential and reconciliation ports. The worker composition cannot inherit a process-global memory/registered/override broker. Composition revision 2 calls the shared `currentProductRoleResolver({signal})`, retaining principal attenuation and binding fresh human reads to the activity's cancellation/deadline signal. Its exact shared helper remains root-owned and must be integrated before compilation or acceptance; there is no copied helper or snapshot fallback. No browser, model or plugin input may supply a runtime or call stores directly. The private factory-issued readiness capability prevents a plain caller-provided ready flag from authorizing provisioning. `createIsolatedReconcileSweepRuntime` is explicitly restricted to `NODE_ENV=test`; its scripted ports provide no production authority.

Provisioning uses the caller's authenticated Temporal client and its configured namespace. Require the existing validated explicit Temporal address, TLS/auth and payload converter. Register `ZenithScheduleOwner` as a **Keyword** in that namespace before provisioning; failure to store that attribute must fail creation. This implementation never changes server search-attribute registrations. Only the provisioning service identity may create/update schedules; operator pause/cancel credentials must remain separately controlled. Never log credentials, payloads, SQL errors or provider responses.

`ensureReconcileSchedule` first verifies local prerequisites. A new Schedule is created paused with exact ownership memo, configuration digest and typed owner attribute. It reads back the interval, policies, action, queue, workflow type/ID, scalar arguments, deadline/retry settings, headers, memo and custom search attributes. An incompatible or foreign existing identity is refused. A compatible existing identity is adopted without mutation, retaining any operator pause or action limit refusal.

Raw fields omitted by SDK 1.24's decoded description are also checked: the action must retain normal/default task-queue kind with no sticky queue name, no worker versioning override, and `keepOriginalWorkflowId` must remain false/default. These fields affect routing and workflow identity in the [workflow](https://github.com/temporalio/api/blob/master/temporal/api/workflow/v1/message.proto), [task queue](https://github.com/temporalio/api/blob/master/temporal/api/taskqueue/v1/message.proto) and [schedule](https://github.com/temporalio/api/blob/master/temporal/api/schedule/v1/message.proto) APIs. Absent/null and inert protobuf defaults are accepted; foreign selections refuse adoption and activation.

Fresh activation changes only `paused` and the fixed note, using the exact described raw Schedule and its `conflictToken`. The installed TypeScript SDK 1.24.0 `ScheduleHandle.update` omits that token; its unconditional read/update is unsuitable for this activation. A concurrent action change or operator pause invalidates the guarded update. A failed or lost update response is read back for compatibility and refused without a repeated write. Retry the provisioning inspection only after checking the actual fixed identity. Never delete/recreate to bypass a conflict or automatically unpause a retained Schedule. The API defines this guard in [UpdateScheduleRequest](https://github.com/temporalio/api/blob/master/temporal/api/workflowservice/v1/request_response.proto), and [SDK scheduling](https://docs.temporal.io/develop/typescript/schedules) describes provisioning operations.

`inspectReconcileSchedule` returns only paused/running/action/overlap/missed-catchup counts after exact compatibility validation. Production health must also publish the latest completed/deferred/failed workflow status, last successful SQL pass time, consecutive deferred results, saturation and unread-node counts. Alert on paused/foreign schedules, overdue successful observation, repeated deferred/timeout results, stuck global leases or sustained saturation. A Temporal action-start counter alone does not prove the controller observed any environment. This candidate provides the inspection projection; root health/metric/alert wiring and operator outage response remain open.
