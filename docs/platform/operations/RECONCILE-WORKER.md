## Configuration and permission

The process requires the existing explicit Temporal address, explicit namespace, actual PostgreSQL handle/current schema, checksum-verified OPA bundle, control signer and packaged OpenTofu/custody prerequisites. Production reconciliation additionally requires configured TLS with an API key or mTLS client pair. Connection success and namespace readback must confirm the configured endpoint; source option validation does not establish live certificate or server authorization acceptance. The same payload converter and configured namespace/identity reach both the native poller and the separately owned scheduling client. Previous encryption keys remain necessary for reading old schedule arguments and workflow results.

| Variable | Default | Accepted values |
| --- | --- | --- |
| `ZENITH_WORKER_RECONCILE_SCHEDULE_MODE` | `observe` | `observe`, `provision` |
| `ZENITH_WORKER_RECONCILE_MAX_ENVIRONMENTS` | `25` | Integer `1..25` |
| `ZENITH_WORKER_RECONCILE_CONCURRENCY` | `3` | Integer `1..3` |

`observe` never creates, activates, updates, deletes, triggers, backfills or unpauses a schedule. A missing or incompatible schedule leaves the actual worker polling with reconciliation readiness unavailable; an operator must investigate the fixed identity. A paused schedule remains paused. `provision` is an explicit operator permission to reach the exact owned schedule creation/fresh activation path. It still refuses foreign configuration, raw routing/identity overrides or unavailable prerequisites. A compatible retained schedule is adopted without mutation, preserving an operator pause. Do not grant create/update rights to the normal observation identity. When using the same worker process for initial provisioning, select an independently authorized provisioning credential and restore the normal poller identity/`observe` mode afterward. Do not treat this configuration value as an authorization grant from Temporal.

`ZenithScheduleOwner` must already be registered as **Keyword** in the configured namespace. This worker does not register attributes or change namespace rights. Server provisioning failures refuse startup; a newly created paused schedule can remain for operator inspection after an uncertain activation. No delete/recreate or automatic unpause attempts follow a failure. Temporal's [TypeScript scheduling guide](https://docs.temporal.io/develop/typescript/workflows/schedules) describes the underlying operations; the candidate's stricter ownership guard still applies.

General worker configuration retains support for arbitrary existing task queues. This durable composition explicitly refuses a worker whose queue differs from `zenith-execution`: it cannot service the fixed sweep. Operators of custom queues need a separately configured fixed-queue worker. Disabling observation to accommodate a custom queue is not a fallback.

## Startup, readiness and shutdown

The process composes the sweep from its actual PostgreSQL handle. The internal broker uses an owning PostgreSQL-bound `PlatformBrokerStore` whose statements use separately bounded transactions, platform scope resolver, canonical policy loader and ready signer. Process-global memory/registered/override brokers cannot replace it. Both memory flags refuse the production factory. A caller's ready flag is not a factory-issued provisioning capability. Revision 2 imports the shared `currentProductRoleResolver({signal})` contract from `src/lib/capabilities/current-product-roles.ts`; the activity's combined cancellation/deadline signal bounds its fresh human reads. The helper preserves canonical system and integration attenuation. Root integrated that unchanged shared dependency from commit `15ce74f81a4919d1d12780d1e7c95445595bbceb`, 4,349 bytes, SHA256 `e5923345950b4edd06a444d42131616b8b5bff987cdb4b2eb1c8534ebeff386c`. There is no copied helper or snapshot fallback. The prepared owning-SQL broker controls use explicitly modeled product scopes/membership and cannot attest live hosted human/provider authority.

After creating the native worker, startup invokes `Worker.run()`, opens its dedicated configured client, then reads the actual normal workflow and activity task-queue pollers. Both must report this configured identity with a last-access time at or after the current startup and no more than five seconds in the future, within a ten-second deadline. Reuse of a stale poller record cannot satisfy that time predicate. Worker/server clocks must be aligned; unconfirmed polling fails startup. This inspection is operational polling evidence, not a distinct authentication identity when operators deliberately reuse the same identity string. Only afterward may explicit provisioning permission be exercised. The pinned [SDK 1.24 worker implementation](https://github.com/temporalio/sdk-typescript/blob/v1.24.0/packages/worker/src/worker.ts) and [Worker API](https://typescript.temporal.io/api/classes/worker.Worker) define polling/draining behavior.

The actual `/readyz` response includes a mandatory `reconciliation` check beside Temporal/store/policy/drivers. Old pure health callers retain their four-check response shape. A running poller, schedule action count or successful empty HTTP probe does not by itself establish observation. The monitor verifies the exact schedule, reads at most three recent action executions, pins the original run ID with `followRuns:false`, and checks type, task queue, terminal status, completion time and count-only result. A prior completed pass can remain current while a newer pass is still running. A newer closed unsuccessful pass cannot borrow that prior success.

Readiness requires a completed SQL pass no older than 180 seconds, no future timestamp beyond the five-second tolerance, and zero failed/deferred/unread/busy counts with neither saturation nor timeout. Completion age is checked again after the awaited result read, immediately before successful readiness; a read crossing the boundary cannot retain an earlier fresh decision. Missing, incompatible, paused, waiting, busy, deferred, stale or unconfirmed execution is unavailable. An empty fleet or graph can confirm a bounded SQL/controller pass; it does not establish a provider read, repair dispatch, whole-fleet capacity or cleanup quiescence. Sustained saturation requires lowering pressure or adding capacity under the existing controller limits, not raising these bounds.

Every 30 seconds the worker logs only a fixed phase, current-observation boolean, running count, confirmed completion timestamp and validated controller counts. Schedule and result reads have ten-second RPC bounds; one inspection may use a schedule read followed by a result read. Concurrent probes share that bounded pending inspection. Neither arguments, workflow IDs, tenant IDs, memo, errors, keys nor provider responses enter this projection. Probe timeouts remain unavailable. Shutdown stops status refreshes, drains the worker before releasing activity resources, then closes probes, the monitor, janitor, dedicated client, native connection and PostgreSQL handle, including startup failures. A failed close does not bypass later resource cleanup. [Connection deadlines and close](https://typescript.temporal.io/api/classes/client.Connection) support the client lifecycle; accepted provider calls remain subject to existing uncertainty semantics.
