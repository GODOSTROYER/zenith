# Durable operation workflow starts

Written against branch `codex/workflow-start-outbox-r4-20261003`, based on durable workflow-start authority input at `15ce74f81a4919d1d12780d1e7c95445595bbceb` (2026-10-03). This source-input pin does not establish runtime acceptance of the additive changes or live-provider behavior. Exact integrated verification remains separate.

This additive contract is source work pending independent review and real PostgreSQL/Temporal verification. It does not change existing starters or workflow histories until their callers are wired explicitly.

`startWorkflowIntent(kind, input)` commits an immutable `platform.workflow_start_intents` row before connecting to Temporal. It then commits a permanent single-attempt CAS before the Start RPC. Production uses the canonical PostgreSQL configuration and a dedicated one-connection handle, so an enclosing application transaction cannot delay the commit until after transport. There is no memory/file fallback, caller approval flag, client override, or authorization callback.

The row binds tenant/operation, supported workflow type and derived ID, frontend/TLS digest, namespace, queue, fixed start settings, immutable proposal/input digests, and a copied own-scalar argument snapshot. `sourceDigest` combines the immutable operation and argument digests; it identifies the request source, not product/source bytes. Extra properties and serialization hooks are not evaluated. Product revision/deployment IDs must match proposal input; a connection ID and a build hint absent from that proposal are retained scalar references, not proof of product-store revision bytes or ownership. `preApproved` remains informational; the concrete-plan activities enforce current approval and mutation authority later. API keys, TLS material, codec keys, URLs, raw results and error details never enter the intent or receipt.

Admission is stage-specific:

- Deploy (including rollback), destroy, day-two and remediation require the existing live claimed `running` operation. The helper does not consume approval again or claim/reopen that operation. Proposal admission can start a workflow before it produces its concrete executable plan; no circular plan-approval prerequisite is introduced.
- Read-only teardown review requires its immutable `infrastructure.plan` intent and an approved/queued operation; its activity takes the execution/environment lease later.
- Recurring reconcile starts, signal delivery and other workflow types are outside this contract.

Every first prepare and dispatch constructs a fixed canonical broker **after** recorded-lease, operation and intent-row locks. It uses `currentProductRoleResolver` with an eight-second abort bound, `platformScopeResolver(tx)`, the canonical credential signer, system clock and policy loader, and `PlatformBrokerStore(tx)`. Process-global broker overrides, registered stores and worker role snapshots cannot authorize these writes. The isolated test factory captures actual dependency ports once at construction, discards the supplied store and checks `NODE_ENV=test` at construction and invocation; callers supply no per-call authority. Production refuses the explicit broker-memory option and a non-PostgreSQL entry handle.

After those locks, one detached, recursively frozen snapshot captures the full workspace policy JSON/version/presence and environment policy JSON/version/autonomy/presence. The evaluator reads exactly this snapshot. Both the prepared INSERT and attempted UPDATE compare it with the current owning SQL state, including same-version JSON changes, default-row insertion/deletion and a globally keyed foreign environment row. A changed snapshot refuses; the helper does not refresh, re-evaluate or retry against replacement settings. The final SQL clock separately checks operation/claim/fence expiry, current round/proposal/plan, exact live human approval IDs/count, consumed state and absence of rejection. A role or policy change during an observed lock wait therefore reaches fresh evaluation; a settings change during a delayed role lookup cannot silently authorize the final CAS. The bounded read-only evaluation cannot commit after abort.

Product membership reads, platform SQL and later Temporal transport remain separate authorities: the final SQL settings fence does not make an independently stored role read or provider write atomic. Mutating activities still check authority at their own boundary.

## Crash and readback contract

| Durable state | Permitted next action |
| --- | --- |
| No committed row | Prepare under current operation authority. No transport has been scheduled by this helper. |
| `prepared` | Fresh canonical authority may claim the one original attempt. Connection/serialization failure before claim leaves this state. |
| `attempted` | Independent readback only, including a claim-commit response loss or crash before transport. Missing execution never permits another Start. |
| `acknowledged` | Read the pinned original run and immutable start event again. Keep the first receipt and its tombstone even if history is absent. |

The Start request uses the stored UUID as Temporal `requestId`, `REJECT_DUPLICATE`, conflict `FAIL`, workflow maximum attempts one, a ten-second workflow-task timeout and a ten-second RPC deadline. SDK transport retry inside this single logical request retains that same UUID; this helper never issues another logical Start after the CAS. A duplicate/failed/timed-out Start response is never enough to adopt an execution.

Readback uses independent Describe identity plus the first history page pinned to the observed original run. It validates workflow ID/type/queue, first/original run IDs, retry/timeout settings, no parent/cron/retry/reset/version override, the internally generated attempt identity, complete decrypted original arguments and exact immutable start memo. Mutable current memo/status and workflow results are not approval or quiescence evidence. Payload conversion uses the configured Temporal codecs with the workflow namespace/ID serialization context. Current SDK/API support must expose `workflowId` in the start event (Temporal 1.21 or later); unavailable fields, missing decryption keys and unsupported inherited-routing fields refuse confirmation.

The additional raw defaults follow the installed official `@temporalio/proto` 1.24.0 definitions, generated by the pinned [SDK proto generator](https://raw.githubusercontent.com/temporalio/sdk-typescript/v1.24.0/packages/proto/scripts/compile-proto.ts). `eagerExecutionAccepted` must be omitted/null/false. Priority may be omitted or have zero/default `priorityKey`, empty `fairnessKey`, and omitted/zero/1.0 `fairnessWeight`; the proto documents 1.0 as the fairness default, and this contract already excludes a calling parent that could supply inheritance. Time skipping may be omitted or disabled with zero/default count and propagation knobs, and no `fastForwardConfig` message. Propagated state may be omitted or have zero skipped seconds **and** nanos and zero count, with no fast-forward target message. A `declinedTargetVersionUpgrade` wrapper, including an empty wrapper recording a declined unversioned target, always refuses. Presence of an empty fast-forward message also refuses. `continuedFailure` and `lastCompletionResult` must each be omitted/null; even an empty message refuses because canonical Start sends no inherited failure or completion input. No other unknown-field rejection is introduced. The fixed settings digest now includes this default-state policy; pre-integration revision 2 source and receipts are preserved, and its differing binding is not silently upgraded.

The broader field descriptions are published in the [Temporal history API](https://raw.githubusercontent.com/temporalio/api/master/temporal/api/history/v1/message.proto) and [workflow-service API](https://raw.githubusercontent.com/temporalio/api/master/temporal/api/workflowservice/v1/request_response.proto); context and codec conversion follow the pinned [TypeScript SDK 1.24.0](https://raw.githubusercontent.com/temporalio/sdk-typescript/v1.24.0/packages/client/src/workflow-client.ts). The checked field layout is the pinned SDK, including `timeSkippingStatePropagation.initialSkippedDuration`, rather than a later API layout.

Late exact readback may append the first acknowledgement after cancellation, expiry, reaper uncertainty or revocation. It changes only the intent receipt. It never changes operation/grant/job/UI state or certifies that provider effects stopped. A different original run or receipt conflicts permanently. SQL DELETE, binding replacement, attempt replacement and phase rollback are refused; the parent operation cannot cascade-delete the tombstone. There is no pruning policy. Migration 12 first revokes all `service_role` table privileges, including creator-default `TRUNCATE`/`REFERENCES`/`TRIGGER`, then grants only SELECT/INSERT/UPDATE. Row DELETE triggers alone cannot prevent TRUNCATE. Root must preserve these exact privileges in the aggregate emitted SQL as well.

An accepted Start with a lost response can therefore recover its receipt independently. A claim committed before a worker crashes **without** sending Start sacrifices automatic liveness: retained absence is uncertainty, never permission to replay. Operator continuation, a new proposal/browser approval, customer-started/reset workflows, durable signals, product outboxes and full writer/quiescence inventory remain separate work. No source-object, cloud atomicity, cleanup clearance, or live Temporal Cloud acceptance is claimed.
